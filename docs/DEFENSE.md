# Шпаргалка к защите (≈10 минут)

Каждый участник должен уметь ответить на всё ниже. Ссылки на файлы — чтобы показать «вживую».

---

## 1. Почему работа разделена именно так? Что если бы всё делал один агент?

**Разделение по типу навыка и по риску:**
- *Researcher* — только веб (поиск, чтение страниц). Нет терминала → не может ничего сломать на машине.
- *Coder* — только код (terminal, execute_code). Нет веба → не тянет непроверенные данные из интернета, работает только с тем, что передал координатор.
- *Coordinator* — только планирование и сборка ответа. Инструменты исполнения отключены (`agent.disabled_toolsets` в `agents/coordinator/config.yaml`).

**Плюсы:**
- У каждого короткий, узкий `SOUL.md` и мало инструментов → модель реже ошибается в выборе инструмента.
- Можно поставить разные модели: дешёвую и быструю для поиска, кодовую для кода, сильную для планирования (см. вопрос 5).
- Изоляция памяти и контекста: длинные веб-страницы не засоряют контекст кодера и наоборот.
- Принцип наименьших привилегий: агент с доступом к shell не читает произвольный интернет (меньше риск prompt injection → выполнение команд).
- Процесс прозрачен: в чате видно, кто что сделал и где ошибка.

**Минусы / что изменилось бы с одним агентом:**
- Один агент был бы **быстрее и дешевле** для простых запросов (нет пересылки сообщений, нет повторного контекста).
- Не нужен протокол передачи и защита от зацикливания.
- Но: один большой промпт + все инструменты сразу, одна модель на всё, весь мусор в одном контексте, больше прав у одного процесса. На составных задачах (данные + анализ) качество и надёжность ниже.

## 2. Как агент понимает, что надо передать работу, и как координатор понимает, что задача закончена?

- **Когда передавать** — решает координатор по правилам в `SOUL.md` + skill `team-handoff` (таблица «нужно факты → researcher, нужен расчёт → coder, оба → T1 потом T2»). Тривиальные вопросы он отвечает сам.
- **Как передаёт** — сообщением `@specialist [Tn] TASK: … RETURN: …`. Hermes будит только упомянутого бота (`exclusive_bot_mentions: true`).
- **Специалисты не передают работу друг другу** — им запрещено упоминать кого-либо кроме координатора. Вся маршрутизация — через координатора (звезда, а не сеть).
- **Как понять, что закончено:** у каждой подзадачи id `[T1]`, `[T2]`. Специалист отвечает ровно одним сообщением с `STATUS: DONE` или `STATUS: FAILED`. Координатор ведёт чек-лист `T1 ✅ T2 ⏳`. Когда все DONE (или FAILED после одной повторной попытки) — пишет `✅ FINAL ANSWER` без упоминаний ботов. Это и есть сигнал завершения.
- **Важная деталь конфигурации:** `group_sessions_per_user: false`. По умолчанию Hermes ведёт отдельную сессию для каждого отправителя в группе — тогда ответ researcher'а попал бы в другую сессию координатора, и он бы «не увидел» результат. Общая сессия на группу решает это.

## 3. Что мешает двум ботам отвечать друг другу бесконечно?

Четыре уровня защиты:
1. **Промпт (`SOUL.md`)**: один ответ на один task id; специалист упоминает только координатора; запрет на «спасибо»-ответы; финальный ответ без упоминаний ботов; лимит 6 делегаций и 1 повтор на запрос.
2. **`exclusive_bot_mentions: true`** — сообщение с `@researcher_bot` обрабатывает только researcher, остальные молчат.
3. **`bots_require_mention: true`** (`TELEGRAM_BOTS_REQUIRE_MENTION`) — сообщение от бота засчитывается только при явном `@mention`. Простой reply/цитата от бота не запускает ответ. Без этого два бота, отвечающие reply друг на друга, зацикливаются.
4. **`gateway.bot_loop_guard`** — жёсткий предохранитель Hermes: больше 20 сообщений от ботов в чате за 5 минут → сообщения от ботов в этом чате игнорируются 10 минут. Сообщения людей не считаются и не блокируются.

Плюс `TELEGRAM_ALLOW_BOTS=mentions` — от других ботов принимаются только сообщения с упоминанием.

Телеграм сам тоже ограничивает: бот получает сообщения других ботов только если включён Bot-to-Bot Communication Mode, и Telegram в документации прямо требует защиту от циклов.

## 4. Покажите запрос, на котором система сломалась. Что пошло не так и как исправить?

См. `docs/FAILURE-LOG.md`. Перед защитой **обязательно воспроизведите хотя бы один случай вживую** и вставьте скриншоты/логи.
Самый наглядный для показа: запрос, для которого researcher не может найти данные (почасовые данные за вчера), — видно ветку `STATUS: FAILED → повтор → частичный ответ`.

## 5. Какие модели у каждого агента и почему? Что будет с моделью поменьше?

| Агент | Модель | Почему |
|---|---|---|
| Coordinator | `claude-haiku-4-5-20251001` | Самое сложное — следовать протоколу (id, STATUS, не упоминать ботов в финале), планировать, сводить результаты. Нужно сильное следование инструкциям. |
| Researcher | `claude-haiku-4-5-20251001` | Маленькая, быстрая и дешёвая модель: много чтения веб-страниц, мало рассуждений. Заодно это живой пример «модели поменьше» в системе. |
| Coder | `claude-haiku-4-5-20251001` | Код нужно не только написать, но и запустить, прочитать ошибку и исправить — сильная модель делает это за меньше попыток. |

Все три от одного провайдера (Anthropic) — один ключ, один счёт; различаются размером/ценой под сложность роли.

*(Если поменяете модели — обновите таблицу; модель можно сменить `hermes -p <agent> model`.)*

**С моделью поменьше:**
- Координатор чаще ломает протокол: забывает `[Tn]`, упоминает бота в финале (→ лишний ответ), отвечает «спасибо» специалисту, делает работу сам или не дожидается всех результатов.
- Малые модели хуже вызывают инструменты: пишут «я поискал», не вызвав `web_search`; говорят «сохранил в память», не вызвав `memory` (это прямо описано в документации Hermes для моделей < ~30B).
- Researcher чаще галлюцинирует источники и числа.
- Coder может выдавать «ожидаемый вывод» вместо реального запуска.
- Защита Hermes (loop guard, require mention) при этом продолжает работать — поэтому она и нужна: не полагаемся только на промпт.

## 6. Как `SOUL.md`, skills и tools меняют поведение агента?

- **`SOUL.md`** — идентичность и правила; Hermes вставляет его в самое начало системного промпта (identity slot). Определяет *кто я, с кем работаю, формат ответа, запреты*. Действует всегда.
- **Skills** (`skills/<name>/SKILL.md`) — процедурная память: пошаговая инструкция для конкретного типа задачи (как искать источники, как запускать анализ, как делегировать). Загружаются по необходимости, а не всегда → экономят контекст. Hermes может сам создавать и улучшать skills после сложных задач.
- **Tools / toolsets** — что агент *физически может* делать. Промпт можно нарушить, а отключённый инструмент — нет. Пример: у координатора нет `terminal`, поэтому даже если модель «захочет» запустить код, она не сможет.

Демонстрация: убрать у researcher'а веб-backend → он отвечает `STATUS: FAILED`; поменять формат RESULT в `SOUL.md` → меняется формат сообщений в чате.

## 7. Что каждый агент помнит между разговорами и где это хранится?

У каждого агента свой Hermes profile = своя папка `~/.hermes/profiles/<agent>/`, памяти не пересекаются.

| Что | Файл | Как используется |
|---|---|---|
| Заметки агента (`memory`) | `memories/MEMORY.md`, до 2 200 символов | Вставляется в системный промпт в начале каждой сессии (замороженный снимок). Агент пишет туда сам через инструмент `memory`. |
| Профиль пользователя (`user`) | `memories/USER.md`, до 1 375 символов | Только у координатора включён: язык, предпочтения человека. |
| Вся история переписки | `state.db` (SQLite + FTS5) | Не попадает в промпт автоматически; агент ищет по ней инструментом `session_search`. |
| Skills | `skills/` | Процедуры; могут дополняться самим агентом. |
| Секреты и настройки | `.env`, `config.yaml` | Не «память», а конфигурация. |

Нюансы: новая запись в память видна только в **следующей** сессии; в Telegram сессия группы длится, пока не напишешь `/new`. Между агентами информация передаётся только через сообщения в Telegram.
