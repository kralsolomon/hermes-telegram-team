## A. Что мы построили

### A.1. В одном абзаце

Telegram-группа, в которой живут **три независимых AI-агента** на базе **Hermes Agent** (open-source агент от Nous Research). У каждого агента — **свой Telegram-бот**, **свой профиль Hermes** (отдельная папка с настройками, промптом, памятью и историей), **своя роль и свои инструменты**. Человек пишет только координатору; координатор разбивает задачу и **передаёт подзадачи специалистам, упоминая их через `@username` в группе**; специалисты отвечают координатору; координатор собирает финальный ответ.

Сценарий использования (use case): **помощник для учёбы и исследований** — вопросы, где нужны **данные из интернета и/или вычисления**: «сравни население двух стран и построй график», «посчитай сложные проценты и покажи по годам», «найди формулу и проверь расчётом».

### A.2. Агенты

| Агент | Бот | Роль | Модель | Включённые инструменты (главное) | Отключено |
|---|---|---|---|---|---|
| **Coordinator** | `@coordinator123123_bot` **[ЗАПОЛНИТЬ свой]** | Принимает запрос человека, планирует, делегирует, собирает финальный ответ | `claude-haiku-4-5-20251001` | memory, skills, session_search, clarify, todo | terminal, code_execution, browser, image_gen, tts |
| **Researcher** | `@researcher123123_bot` | Ищет факты и числа в интернете, возвращает краткую сводку с источниками | `claude-haiku-4-5-20251001` | web (web_search, web_extract через Tavily), memory, skills | terminal, code_execution, browser, file, vision, todo, clarify, cronjob, delegation, session_search |
| **Coder** | `@coder123123_bot` | Пишет и **запускает** Python: расчёты, таблицы, графики matplotlib | `claude-haiku-4-5-20251001` | terminal, code_execution, file, memory, skills | web, browser, image_gen, tts, delegation, session_search |

Все три — на одном провайдере (Anthropic API, один ключ). Модель одинаковая из-за бюджета ($4); архитектура позволяет поставить каждому свою (см. D.5).

### A.3. Как проходит один запрос (поток сообщений)

```
Человек:      @coordinator_bot Сравни население KZ и UZ за 2015–2024 и построй график
Coordinator:  План: T1 → Researcher (данные), T2 → Coder (расчёт и график)
Coordinator:  @researcher_bot [T1] TASK: найди население по годам… RETURN: таблица + источники
Researcher:   @coordinator_bot [T1] RESULT  <таблица>  Sources: …  STATUS: DONE
Coordinator:  @coder_bot [T2] TASK: вот данные <вставлены>, посчитай рост и построй график. RETURN: …
Coder:        @coordinator_bot [T2] RESULT  <числа, код>  MEDIA:/…/chart.png  STATUS: DONE
Coordinator:  ✅ FINAL ANSWER  <сводка, источники, график>   ← без @упоминаний ботов = конец
```

Топология — **«звезда»**: специалисты никогда не общаются друг с другом напрямую, всё идёт через координатора.

### A.4. Протокол передачи работы (handoff protocol)

1. **ID подзадачи** `[T1]`, `[T2]`… — чтобы сопоставить ответ с задачей и знать, что ещё не пришло.
2. **TASK** — самодостаточная инструкция: всё нужное (включая данные из предыдущих шагов) — внутри сообщения.
3. **RETURN** — точный формат ожидаемого ответа (таблица, PNG, список ссылок).
4. **RESULT** + **STATUS: DONE / FAILED** — специалист отвечает **ровно одним** сообщением на задачу.
5. **✅ FINAL ANSWER** без упоминаний ботов — сигнал конца разговора.
6. Лимиты: **не больше 6 делегаций** на один запрос человека, **не больше 1 повтора** упавшей подзадачи.

### A.5. Архитектура (физически)

```
Windows 11
 └─ WSL 2 (Ubuntu)
     └─ Hermes Agent v0.21.5  (~/.hermes)
         ├─ default profile        — только «хост» для общего gateway
         ├─ profiles/coordinator   — SOUL.md, config.yaml, .env, skills/, memories/, state.db
         ├─ profiles/researcher    — то же
         └─ profiles/coder         — то же
         └─ ОДИН процесс gateway (multiplex) ⇄ Telegram Bot API
               ├─ long polling бота coordinator (свой токен)
               ├─ long polling бота researcher  (свой токен)
               └─ long polling бота coder       (свой токен)
     LLM: Anthropic API (claude-haiku-4-5)      Web search: Tavily (без ключа)
```

Важно: **gateway** — это процесс, который держит связь с Telegram (опрашивает Bot API, получает сообщения, передаёт агенту нужного профиля, отправляет ответы). В Hermes 0.21 один gateway обслуживает все профили (**multiplexing**), но **у каждого профиля свой токен, свой промпт, свои настройки, своя память**.

### B.1. `SOUL.md` — «душа» агента (системный промпт)

**Что это в Hermes:** файл `~/.hermes/profiles/<агент>/SOUL.md`. Hermes вставляет его **в самое начало системного промпта** (identity slot). Это определяет, **кто агент, что он делает, в каком формате отвечает, чего не делает**. Действует на каждом шаге каждой сессии.

**Шаблоны.** В репозитории вместо реальных username стоят метки `{{COORDINATOR}}`, `{{RESEARCHER}}`, `{{CODER}}`. `setup.sh` подставляет туда значения из `.env`. Зачем: репозиторий не привязан к нашим конкретным ботам — любой может склонировать и подставить своих.

#### `agents/coordinator/SOUL.md`
- **Таблица команды**: кто есть кто и для чего его звать.
- **Алгоритм на каждый запрос**: план → объявить план → делегировать (формат TASK/RETURN) → ждать RESULT → FINAL ANSWER.
- **Тривиальные вопросы отвечает сам** (приветствие, вопрос о команде) — зачем гонять специалистов и тратить деньги.
- **Правило про `@username`**: писать `@бота` только первым словом TASK-сообщения; в плане/описании/финале — только имена (Researcher, Coder). *Зачем*: каждое `@` будит бота (добавлено после сбоя F6).
- **Если T2 зависит от T1** — дождаться T1 и вставить данные в T2. *Зачем*: специалист надёжно видит только адресованное ему сообщение.
- **Финальный ответ без `@ботов`** — сигнал конца, защита от цикла.
- **Лимиты**: 6 делегаций, 1 повтор, никаких «спасибо» специалистам.
- **Не делать работу специалистов** самому (у него и инструментов таких нет).
- **Язык ответа = язык человека** (RU/KZ/EN).

#### `agents/researcher/SOUL.md`
- Роль: поиск и краткая сводка **с источниками**.
- Формат ответа: первая строка строго `@{{COORDINATOR}} [Tn] RESULT`, потом ответ, `Sources:`, `STATUS:`.
- **Ровно один ответ на задачу**; молчать на всё, что не TASK для него.
- **Никаких других `@username`** (после сбоя F5 убрали username кодера из промпта исследователя совсем).
- Не писать код, не выдумывать числа и источники, ≤250 слов.

#### `agents/coder/SOUL.md`
- Роль: писать и **запускать** Python (stdlib, numpy, pandas, matplotlib).
- Данные — **только из TASK**, в интернет не ходит.
- До 3 попыток исправить ошибку, потом `STATUS: FAILED` с последней ошибкой.
- График сохраняет в PNG и прикладывает через `MEDIA:/абсолютный/путь.png` — так Hermes отправляет файл в Telegram как картинку.
- Запрет деструктивных команд (`rm -rf` и т.п.).
- Показывать **реально вычисленные** числа.

### B.2. `config.yaml` — настройки агента

Копируется в `~/.hermes/profiles/<агент>/config.yaml`. Разбор каждого блока:

#### `model`
```yaml
model:
  provider: anthropic
  default: claude-haiku-4-5-20251001
```
Какая LLM. Ключ API берётся из `.env` профиля (`ANTHROPIC_API_KEY`).

#### `agent.disabled_toolsets`
Какие наборы инструментов **отключены**. Это **принцип минимальных привилегий**:
- координатор без `terminal`/`code_execution` — физически не может запустить код;
- исследователь без `terminal`/`code_execution`/`file` — не может ничего сломать на машине, хотя читает произвольные веб-страницы (а это главный вектор prompt injection);
- кодер без `web`/`browser` — не тянет непроверенные данные из интернета и не может «утечь» наружу через веб.

Почему важно: **промпт — это просьба, отключённый инструмент — это гарантия**. Модель может нарушить инструкцию, но не может вызвать несуществующий инструмент.

Дополнительный эффект: **меньше инструментов → меньше токенов** (описание каждого инструмента отправляется модели при каждом вызове) → дешевле и меньше путаницы у маленькой модели.

`session_search` отключён у специалистов (после сбоя F7) — им не нужно вспоминать прошлые разговоры, а копирование старых форматов вредило.

#### `group_sessions_per_user: false`
По умолчанию Hermes в группе ведёт **отдельную сессию на каждого отправителя**. Тогда сообщение человека попадало бы в одну сессию координатора, а RESULT от бота-исследователя — в другую, и координатор **не видел бы результат рядом со своим планом**. `false` = **одна общая сессия на группу** («общий мозг комнаты»).

#### `telegram:`
| Ключ | Координатор | Специалисты | Зачем |
|---|---|---|---|
| `require_mention` | true | true | Реагировать только когда обратились (`@`, ответ на сообщение бота, команда). Иначе бот отвечал бы на каждое сообщение в группе. |
| `exclusive_bot_mentions` | **false** | true | При `true`: если в сообщении явно упомянут бот X, обрабатывает **только X**. У специалистов — чтобы `@coder_bot …` не будил исследователя. У координатора `false` — чтобы он реагировал на реплай специалиста, даже если тот ошибся с `@` (страховка, см. F5/F7). |
| `bots_require_mention` | **false** | true | При `true`: сообщение **от другого бота** засчитывается только с явным `@этот_бот`; простой реплай от бота игнорируется. Это закрывает классический цикл «два бота отвечают реплаями друг другу». У координатора `false` — он должен просыпаться на реплай специалиста. Цикла нет, потому что у специалистов `true`: реплай координатора их не будит. |
| `observe_unmentioned_group_messages` | true | false | Координатор «видит» всю ветку как контекст (не отвечая), специалисты — только адресованное им. |
| `reactions` | true | true | 👀 / 👍 / 👎 на сообщениях — видно, кто работает (удобно на демо). |

Те же значения продублированы в `.env` профиля (`TELEGRAM_*`), чтобы не зависеть от того, что из них Hermes читает приоритетнее.

#### `gateway.bot_loop_guard`
```yaml
gateway:
  bot_loop_guard: { enabled: true, max_events: 20, window_seconds: 300, cooldown_seconds: 600 }
```
**Аварийный тормоз Hermes**: если в одном чате за 5 минут больше 20 сообщений **от ботов**, сообщения ботов в этом чате игнорируются 10 минут. Сообщения людей не считаются и не блокируются. Это последний уровень защиты от бесконечного цикла, не зависящий от модели.

#### `memory`
```yaml
memory:
  memory_enabled: true          # MEMORY.md — заметки агента
  user_profile_enabled: true    # USER.md — только у координатора
  write_approval: false
```
`USER.md` (профиль пользователя) включён только у координатора — только он общается с человеком.

#### `display.memory_notifications: off`
Не писать в чат «💾 Memory updated» — чище группа.

#### `auxiliary.background_review.enabled: false`
После каждого ответа Hermes по умолчанию запускает **фоновую самопроверку**: повторно прогоняет разговор через модель, чтобы решить, что сохранить в память и навыки. Это **почти удваивает расход токенов**. При бюджете $4 — отключили. Побочный плюс: агенты не «учатся» на ошибочных прогонах.

#### `web.backend: tavily` (исследователь)
Бэкенд веб-поиска. Tavily работает **без ключа** (с лимитом запросов). Ключ можно добавить в `.env` (`TAVILY_API_KEY`) для больших лимитов.

#### `terminal` (кодер)
```yaml
terminal: { backend: local, cwd: /home/<user>/hermes-team-workspace/coder, timeout: 120 }
```
Где выполняются команды кодера: `local` = прямо в Ubuntu (WSL). `cwd` — рабочая папка (графики в `out/`). Для изоляции можно `backend: docker`.

### B.3. Skills — `skills/<имя>/SKILL.md`

**Что это:** процедурная память — пошаговая инструкция для **определённого типа задачи**. В отличие от `SOUL.md`, skill **подгружается по необходимости** (агент видит список навыков с описаниями и открывает нужный), поэтому не занимает контекст постоянно. Формат — Markdown с заголовком (frontmatter) `name` и `description`; по `description` агент решает, когда навык применить.

| Skill | Агент | Содержание |
|---|---|---|
| `team-handoff` | Coordinator | Таблица «когда делегировать», шаблоны сообщений, конечный автомат `PLANNED → WAITING → FINAL` (+ ветка FAILED → retry), лимиты, полный разобранный пример |
| `source-brief` | Researcher | Как переформулировать запрос, иерархия надёжности источников (офиц. статистика → World Bank/UN/OECD → статьи → СМИ → Википедия только для поиска первоисточника), открывать первоисточник, а не верить сниппетам, формат вывода, когда честно писать FAILED |
| `analysis-run` | Coder | Данные из TASK вставить в скрипт, `matplotlib.use("Agg")` (без дисплея), сохранить PNG, ≤3 попытки, sanity-check единиц и сумм, `MEDIA:` с абсолютным путём |

Ещё Hermes ставит каждому профилю **~58 встроенных навыков** (bundled skills). Hermes умеет **сам создавать и улучшать навыки** после сложных задач (learning loop) — мы это ограничили, отключив background review.

### B.4. `.env.example` и `.env` — секреты

| Переменная | Что |
|---|---|
| `ANTHROPIC_API_KEY` | ключ к Claude API |
| `TAVILY_API_KEY` | (необязательно) ключ веб-поиска |
| `TELEGRAM_ALLOWED_USERS` | ваш числовой Telegram ID — кто может вызывать ботов |
| `TELEGRAM_GROUP_CHAT_ID` | ID группы (отрицательное число `-100…`) — в какой группе боты работают |
| `*_BOT_TOKEN` ×3 | токены трёх ботов от BotFather |
| `*_BOT_USERNAME` ×3 | username ботов без `@` (подставляются в SOUL.md) |

`.env` в `.gitignore` → в репозиторий не попадает (требование задания). `setup.sh` раскладывает **по-профильный** `.env` (`~/.hermes/profiles/<агент>/.env`, права 600): у каждого **только свой** токен бота + общие настройки доступа:
```
TELEGRAM_BOT_TOKEN=…                 # свой бот
TELEGRAM_ALLOWED_USERS=…             # кто может писать
TELEGRAM_GROUP_ALLOWED_CHATS=…       # в какой группе любой участник (в т.ч. боты) авторизован
TELEGRAM_ALLOW_BOTS=mentions         # сообщения от других ботов принимаются только с упоминанием
TELEGRAM_BOTS_REQUIRE_MENTION=…      # true у специалистов, false у координатора
TELEGRAM_REQUIRE_MENTION=true
TELEGRAM_EXCLUSIVE_BOT_MENTIONS=…    # true у специалистов, false у координатора
ANTHROPIC_API_KEY=…
```
Почему важно `TELEGRAM_GROUP_ALLOWED_CHATS`: сообщения от **ботов** не из списка `ALLOWED_USERS` (это люди), поэтому без разрешения на уровне группы Hermes отклонял бы сообщения ботов друг другу.

### B.5. `scripts/setup.sh`

Запускается после любого изменения в `agents/` или `.env`. Шаги:
1. Проверяет, что `hermes` установлен и `.env` существует.
2. Читает `.env` (убирая Windows-переводы строк `\r`).
3. Проверяет, что все нужные переменные заполнены и что **три username разные** (защита от нашей реальной ошибки F5).
4. Печатает `Usernames: coordinator=@… researcher=@… coder=@…` — чтобы глазами проверить.
5. Для каждого агента:
   - `hermes profile create <агент>` (если профиля нет) — создаёт `~/.hermes/profiles/<агент>/` + команду-ярлык `<агент>`;

**Важно:** после `setup.sh` нужно **перезапустить gateway** (он читает настройки при старте) и **начать новую сессию**.

### B.6. `scripts/team.sh`

```bash

В Hermes 0.21 **нельзя** запускать отдельный gateway на каждый профиль (Hermes отказывает: двойная привязка токенов/портов). Правильно — **один host gateway** на default-профиле с `gateway.multiplex_profiles: true`; он автоматически обслуживает все профили. `team.sh` это и делает. Для отладки удобнее `hermes gateway run` — работает в окне и показывает всё в реальном времени.

## D. Семь официальных вопросов

### D.1. Почему работа разделена именно так? Что если бы всё делал один агент?

**Принцип разделения — по типу навыка и по уровню риска:**
- **Researcher** — работает с недоверенным внешним контентом (веб). Ему **не дан** терминал/код → даже если страница содержит prompt injection («выполни rm -rf»), выполнить нечем.
- **Coder** — может выполнять код на машине. Ему **не дан** веб → он работает только с данными, которые прошли через координатора. Это разрыв цепочки «прочитал вредный текст → выполнил команду».
- **Coordinator** — только планирование и сборка; инструменты исполнения отключены.

**Преимущества разделения:**
1. **Узкие промпты и мало инструментов** → маленькая модель реже ошибается в выборе инструмента и формате.
2. **Разные модели под задачу** (можно сильную для планирования, дешёвую для поиска).
3. **Изоляция контекста**: длинные веб-страницы не засоряют контекст кодера; трассировки кода — контекст исследователя.
4. **Изоляция памяти**: у каждого свой `MEMORY.md`, `state.db`.
5. **Наименьшие привилегии** (безопасность, см. выше).
6. **Прозрачность и отладка**: в чате видно, кто что сделал и на каком шаге сломалось (именно так мы нашли F5).
7. **Параллельность**: независимые подзадачи можно раздать одновременно.

**Что было бы с одним агентом:**
- ➕ **Быстрее и дешевле**: нет пересылки сообщений, системный промпт и контекст не дублируются трижды (у нас один вызов модели ≈ 15K токенов на каждого агента; три агента ≈ втрое больше).
- ➕ **Нет протокола, нет циклов, нет проблем с доставкой** (все наши F5–F7 исчезли бы).
- ➖ Один большой промпт, все инструменты сразу → больше путаницы; все данные в одном контексте; один процесс имеет и веб, и shell → выше риск; одна модель на всё.
- **Вывод:** для простых запросов один агент лучше; мультиагентность окупается на **составных задачах** (данные + анализ), при требованиях к **безопасности** и **разным моделям**. Честно: у нас на заданиях уровня «посчитай проценты» один агент справился бы не хуже.

Дополнительно: Hermes умеет и **встроенных субагентов** (`delegate_task`) внутри одного процесса — это альтернатива; мы использовали отдельных ботов, потому что так требует задание и это даёт независимые профили/модели/память.

### D.2. Как агент понимает, что надо передать работу, и как координатор понимает, что задача закончена?

**Когда передавать** — решает координатор по `SOUL.md` и skill `team-handoff`:
- нужны свежие факты/числа/источники → Researcher;
- нужен расчёт/таблица/график → Coder (данные должны быть в задаче);
- нужно и то и другое → T1 Researcher, затем T2 Coder с данными из T1;
- тривиально → отвечает сам.

**Как передаёт** — сообщением в группе `@specialist [Tn] TASK … RETURN …`. Технически: Hermes-gateway специалиста видит упоминание своего username → `require_mention` пройден → `exclusive_bot_mentions` гарантирует, что проснётся только он → запускается ход агента.

**Специалисты не передают работу друг другу** — только координатору (топология «звезда»): проще контроль и подсчёт подзадач, меньше риск цикла.

**Как координатор понимает, что закончено:**
- каждая подзадача имеет ID; специалист возвращает ровно один RESULT с `STATUS: DONE/FAILED`;
- координатор ведёт чек-лист `T1 ✅ T2 ⏳`;
- все ✅ (или ❌ после одного повтора) → `✅ FINAL ANSWER` **без упоминаний ботов** → никто больше не просыпается → разговор окончен.

**Как координатор вообще «узнаёт», что пришёл результат** (технически): специалист пишет `@coordinator …` и **отвечает реплаем на сообщение координатора**. У координатора `bots_require_mention: false` и `exclusive_bot_mentions: false` → его будит и упоминание, и реплай. Благодаря `group_sessions_per_user: false` результат попадает **в ту же сессию**, где лежит план.

**Ограничение (честно):** нет таймаута. Если специалист не ответил вовсе (упал, закончились деньги), координатор будет ждать. Улучшение: cron-проверка «есть ли незакрытые Tn старше N минут» или явный таймаут в протоколе.

### D.3. Что мешает двум ботам отвечать друг другу бесконечно?

**Пять уровней защиты (от «мягкого» к «жёсткому»):**
1. **Промпт**: один ответ на ID; специалисты не упоминают никого, кроме координатора; запрет «спасибо»; финальный ответ без `@`; лимит 6 делегаций и 1 повтор.
2. **Топология «звезда»**: специалисты не говорят друг с другом → нет пары «специалист↔специалист», которая могла бы зациклиться.
3. **`require_mention` + `exclusive_bot_mentions`** (Hermes): бот реагирует только когда обращаются именно к нему.
4. **`bots_require_mention: true` у специалистов** (Hermes): сообщение **от бота** засчитывается только с явным `@`; реплай от бота **не** будит. Поэтому: координатор отвечает реплаем специалисту — специалист не просыпается. Цикл «реплай на реплай» разорван.
   - Координатор — исключение (`false`), ему нужно просыпаться на реплаи специалистов. Это безопасно, потому что **разрыв на стороне специалистов**: что бы ни написал координатор реплаем, специалист не проснётся без явного `@`.
5. **`gateway.bot_loop_guard`** (Hermes): >20 сообщений ботов за 5 минут в чате → сообщения ботов игнорируются 10 минут. Не зависит от модели вообще.

Плюс **Telegram** сам по умолчанию не доставляет сообщения ботов ботам (нужен Bot-to-Bot mode), и в документации Telegram прямо требует от разработчиков защиту от циклов: дедупликация, лимиты частоты, ограничение глубины. Hermes также **дедуплицирует повторные `update_id`**.

**Можно показать:** в нашем логе F5 исследователь проснулся по ошибке и ответил реплаем кодеру — кодер **не** ответил (у него `bots_require_mention: true`). Цикл не возник.

### D.4. Покажите запрос, на котором система сломалась. Что пошло не так и как исправить?

**Основной пример — F5 → F7** (рассказывать как историю, ~1.5 мин):

> «Запрос: посчитай сложные проценты 500 000 под 14% на 5 лет. Кодер правильно посчитал и построил график, но адресовал результат `@researcher_bot` вместо координатора. Координатор не проснулся, финального ответа не было, а исследователь проснулся зря и написал “I should stay silent”.

Тогда посмотрели **готовый промпт**, который реально получает агент: `cat ~/.hermes/profiles/coder/SOUL.md` — там было написано “Coordinator: @researcher_bot”. ### D.5. Какие LLM у каждого агента и почему? Что будет с моделью поменьше?

**Сейчас:** все три — `claude-haiku-4-5-20251001` (Anthropic API).

**Почему:**
- **Бюджет** ($4 на API). Один вызов модели агентом ≈ 15K входных токенов (системный промпт + описание инструментов + навыки); один запрос пользователя = 10–20 вызовов на три агента. Haiku — самая дешёвая модель в списке, на ней хватает на десятки прогонов; на Sonnet — на несколько.
- **Достаточно**: задачи у специалистов простые (поиск, короткий скрипт), а формат мы закрепили шаблонами и навыками.
- Один провайдер = один ключ, один счёт.

**Как было бы правильно при нормальном бюджете (и почему):**

| Агент | Модель | Обоснование |
|---|---|---|
| Coordinator | сильная (Sonnet-класс) | Самая сложная роль: планирование, протокол, сведение результатов, учёт подзадач |
| Researcher | дешёвая/быстрая с длинным контекстом (Haiku-класс) | Много чтения, мало рассуждения |
| Coder | средняя/сильная или код-специализированная | Написать → запустить → прочитать ошибку → исправить |

Поменять модель агента: `model.default` в `agents/<агент>/config.yaml` → `setup.sh` → перезапуск. Или `hermes -p <агент> model`.

**Что будет с моделью поменьше — мы это видели вживую:**
- **Не умеет промолчать**: исследователь, разбуженный по ошибке, писал «I stay silent…» вместо молчания (F8).
- **Копирует форматы из контекста** сильнее, чем следует инструкциям: кодер повторял свой старый неправильный адрес (F7).
- **Нарушает мелкие правила протокола**: координатор писал план и TASK одним сообщением, хотя в промпте «отдельно».
- Ещё более мелкие модели (<~30B, по документации Hermes): «говорят», что вызвали инструмент или сохранили память, **не вызвав его**; выдумывают источники и числа; выдают «ожидаемый вывод» вместо реального запуска кода.
- **Поэтому** критичные вещи мы обеспечиваем **настройками Hermes**, а не промптом: доставка (реплай), остановка цикла (`bots_require_mention`, `bot_loop_guard`), права (отключённые инструменты).

### D.6. Как `SOUL.md`, skills и tools меняют поведение агента?

| Механизм | Что определяет | Когда действует | Насколько «жёстко» | Наш пример |
|---|---|---|---|---|
| **SOUL.md** | Личность, роль, правила, формат | Всегда — начало системного промпта | Мягко: модель может нарушить | Формат `[Tn] RESULT … STATUS:` |
| **Skills** | Процедура для типа задачи | Подгружается при необходимости | Мягко, но конкретнее и детальнее | `analysis-run`: Agg backend, ≤3 попыток, MEDIA: |
| **Tools / toolsets** | Что агент **физически может** | Всегда | **Жёстко**: нет инструмента — нет действия | У координатора нет `terminal` |

**Аналогия:** SOUL.md — должностная инструкция, skill — регламент конкретной операции, tools — какие ключи и инструменты выданы сотруднику.

**Как показать вживую:**
- Изменить формат RESULT в `SOUL.md` → `setup.sh` → перезапуск → `/new` → формат в чате меняется.
- Убрать у исследователя `web` (или веб-бэкенд) → он вернёт `STATUS: FAILED`.
- Спросить координатора «запусти python» → не сможет (нет инструмента), предложит передать кодеру.

**Важный нюанс (из нашего опыта):** поведение определяет не только `SOUL.md`, а **весь контекст**: SOUL.md + память + история сессии + навыки + описания инструментов. История сессии может «перевесить» промпт (F7).

### D.7. Что каждый агент помнит между разговорами и где это хранится?

У каждого агента **свой профиль** = своя папка `~/.hermes/profiles/<агент>/`. Памяти **не пересекаются**; общаются агенты **только через сообщения в Telegram**.

| Вид памяти | Где | Объём | Как попадает к модели | У кого |
|---|---|---|---|---|
| **Заметки агента** | `memories/MEMORY.md` | ≤2 200 символов (~800 токенов) | Вставляется в системный промпт **в начале каждой сессии** (замороженный снимок) | все три |
| **Профиль пользователя** | `memories/USER.md` | ≤1 375 символов | То же | только координатор |
| **История всех разговоров** | `state.db` (SQLite + полнотекстовый поиск FTS5) | без лимита (автоочистка закрытых сессий через 90 дней) | Текущая сессия — целиком в контексте; старые — через инструмент `session_search` | у всех хранится; поиск только у координатора |
| **Навыки** | `skills/` | — | Список в промпте, содержимое по запросу | все |
| **Личность** | `SOUL.md` | — | Каждый раз | все |
| **Настройки/секреты** | `config.yaml`, `.env` | — | Не память, конфигурация | все |

**Как это работает:**
- Агент **сам** решает, что записать в память, через инструмент `memory` (add / replace / remove). Если лимит переполнен — инструмент возвращает ошибку, агент должен сжать записи.
- Новая запись в `MEMORY.md` видна только **в следующей** сессии (снимок «заморожен» на старте — ради кэша промпта).
- В Telegram сессия группы **не заканчивается сама** (ни по времени, ни по перезагрузке) — только `/new` (`/new@бот` каждому боту в группе с несколькими ботами).

**Что мы узнали на практике (F7):** `/new` не всегда очищает «то, что модель видит»: старые сообщения из истории (`state.db`) продолжали влиять на поведение. Полный сброс — остановить gateway и убрать `state.db*` профиля (у нас — перенесли в бэкап). `MEMORY.md` у наших агентов был пуст (background review отключён), т.е. проблема была именно в истории.

## E. Дополнительные вероятные вопросы

### E.1. Hermes Agent

**Что такое Hermes Agent?** Open-source (MIT) агент от Nous Research: агентный цикл с инструментами (веб, терминал, файлы, браузер, код…), постоянная память, навыки (с самообучением), планировщик cron, **gateway** к мессенджерам (Telegram, Discord, Slack, WhatsApp, Signal…), профили для нескольких агентов на одной машине. Работает с любым LLM-провайдером (Anthropic, OpenRouter, OpenAI, локальные модели).

**Что такое профиль?** Отдельная «домашняя папка» Hermes (`HERMES_HOME`) со своими `config.yaml`, `.env`, `SOUL.md`, памятью, сессиями, навыками. Создаётся `hermes profile create <имя>`, управляется `hermes -p <имя> …`. Документация прямо запрещает запускать два агента на одном профиле — они будут портить друг другу память.

**Профиль — это песочница?** **Нет.** Профиль изолирует состояние Hermes, но на `local`-бэкенде агент имеет те же права в файловой системе, что и ваш пользователь. Для изоляции — `terminal.backend: docker` или SSH на отдельную машину.

**Что такое gateway? Почему один на всех?** Процесс, связывающий агентов с мессенджерами. В Hermes 0.21 один **host gateway** (на default-профиле, `gateway.multiplex_profiles: true`) обслуживает все профили: для каждого — свой Telegram-адаптер со своим токеном, свои настройки, своя маршрутизация сессий. Раньше было «один gateway на профиль»; новая версия запрещает это, чтобы два процесса не опрашивали один токен и не конфликтовали портами.

**Polling или webhook?** **Long polling**: gateway сам периодически спрашивает у Telegram «есть новые сообщения?». Не нужен публичный адрес/порт — подходит для ноутбука/WSL. Webhook — когда Telegram сам шлёт запросы на ваш HTTPS-адрес (для облачных серверов, которые засыпают).

**Как Hermes решает, отвечать ли на сообщение в группе?** Цепочка фильтров: авторизация (пользователь/чат в списке) → сообщение от бота? (`allow_bots`, `bots_require_mention`) → `require_mention` (есть `@`, реплай, команда, wake-word) → `exclusive_bot_mentions` (упомянут ли явно другой бот) → `ignored_threads` → запуск хода агента.

**Что за «✅ Approved once by ?»** Hermes спрашивает подтверждение на потенциально опасные действия (запуск команд, установка пакетов). Ответ «да» в чате = разовое разрешение. На демо можно заранее поставить пакеты, чтобы запросов было меньше.

**Что такое `MEDIA:`?** Тег в ответе агента: `MEDIA:/путь/к/файлу.png` — gateway вырезает его и отправляет файл как вложение Telegram.

**Что такое background review / learning loop?** После хода Hermes в фоне просматривает разговор и решает, сохранить ли что-то в память или создать/улучшить навык. Это «самообучение» Hermes. Мы отключили (экономия ~×2 токенов + не учиться на ошибочных прогонах).

### E.2. Telegram

**Почему боты не видят друг друга по умолчанию?** Это политика Telegram против спама и циклов. Нужен **Bot-to-Bot Communication Mode** (BotFather). Бот получает сообщение другого бота, если оно содержит команду с его username или является **реплаем** на его сообщение; с режимом bot-to-bot + админ + privacy off — и обычные сообщения.

**Что такое Group Privacy?** Режим, при котором бот в группе видит только команды, реплаи на свои сообщения и сервисные события. Выключили, чтобы видеть упоминания и контекст.

**Зачем боты — админы?** Админ получает все сообщения группы независимо от privacy и (с bot-to-bot) сообщения других ботов.

**Почему ID группы отрицательный?** Так Telegram нумерует группы/супергруппы (`-100…` для супергрупп).

**Почему `/new` надо писать как `/new@bot`?** В группе с несколькими ботами команда без адреса неоднозначна; с `require_mention` и `exclusive_bot_mentions` команду принимает только тот бот, чей username указан.

**Что если один токен использовать в двух местах?** Telegram отдаёт обновления только одному опрашивающему → ошибка `Conflict: terminated by other getUpdates`. Hermes блокирует такой запуск («token lock»).

### E.3. Архитектура и дизайн

**Почему «звезда», а не «каждый с каждым»?** Проще контроль (один учитывает подзадачи), меньше путей для цикла, понятная ответственность. Минус — координатор — узкое место и единая точка отказа.

**Что если координатор упадёт?** Специалисты ничего не будут делать (никто не раздаёт задачи). Человек может обратиться к специалисту напрямую (`@researcher_bot …`) — он ответит, но без сборки. Улучшение — резервный координатор или таймауты.

**Почему специалист не может видеть всю переписку?** У специалистов `observe_unmentioned_group_messages: false` — они видят только адресованное им. Плюсы: меньше токенов, нет путаницы, сложнее prompt injection из чужих сообщений. Поэтому TASK должен быть самодостаточным.

**Как добавить четвёртого агента (например, Writer)?** Новый бот в BotFather (privacy off, bot-to-bot on, админ) → `agents/writer/{SOUL.md,config.yaml,skills/}` → строки в `.env` и `setup.sh` (массивы AGENTS/TOKEN/DESC и подстановка `{{WRITER}}`) → строка в таблице команды в `SOUL.md` координатора → `setup.sh` → перезапуск gateway. Multiplexed gateway подхватит новый профиль сам.

**Можно ли параллельно?** Да: независимые подзадачи координатор отправляет подряд; Hermes обрабатывает обновления разных ботов параллельно (у каждого профиля своя сессия).

**Почему не A2A / встроенные субагенты Hermes?** Hermes поддерживает `delegate_task` (субагенты в одном процессе) и протокол A2A. Задание требует именно **разных Telegram-ботов, общающихся через @упоминания в группе** — это делает взаимодействие видимым и проверяемым. Минус нашего способа — Telegram как шина медленнее и ненадёжнее прямого вызова; плюс — полная прозрачность, независимые профили и модели.

**Как специалист получает данные от другого специалиста?** Только через координатора: координатор вставляет результат T1 в текст T2.

### E.4. Надёжность и ограничения

**Какие слабые места у системы?**
1. Нет таймаутов на подзадачи.
2. Протокол держится на дисциплине модели (частично подстраховано конфигом).
3. Маленькая модель иногда шумит («I stay silent»).
4. Telegram-сообщения ≤4096 символов → длинные ответы режутся на части.
5. Боты работают, пока открыт WSL/компьютер не спит.
6. Tavily без ключа имеет лимит запросов.
7. Одна общая сессия группы растёт → нужно периодически `/new`.

**Что бы улучшили?** Таймауты и повтор через cron; Sonnet-класс для координатора; Docker-бэкенд для кодера; отдельная тема (topic) Telegram на каждый запрос; структурированный JSON вместо текстового протокола; запуск на сервере через `hermes gateway install` (systemd).

**Как проверяете корректность ответа?** Кодер показывает реальный вывод и код; исследователь — источники; координатор не придумывает числа сам. Мы проверяли расчёты вручную (500 000 × 1,14⁵ = 962 707; 3 000 000 × 1,08⁴ = 4 081 466,88 ✅).

**Что происходит, если специалист вернул FAILED?** Координатор повторяет задачу **один раз** с более ясной формулировкой; если снова FAILED — честно сообщает в финальном ответе, что не удалось.

**Что если человек напишет специалисту напрямую?** Специалист ответит кратко и предложит обратиться к координатору для многошаговых задач (правило в SOUL.md).

**Что если посторонний напишет боту?** Hermes отклонит: пользователь не в `TELEGRAM_ALLOWED_USERS`, а чат не в `TELEGRAM_GROUP_ALLOWED_CHATS`.

### E.5. Безопасность

**Где хранятся ключи?** Только в `.env` (корневой) → копии в `~/.hermes/profiles/<агент>/.env` с правами 600. В git не попадают (`.gitignore`). Если токен утёк — `/revoke` в BotFather.

**Риски prompt injection?** Исследователь читает недоверенные страницы → может прочитать «инструкцию» от злоумышленника. Защита: у него **нет** терминала/кода/файлов; кодер **не** ходит в интернет; координатор не исполняет код. Hermes также сканирует записи в память на injection-паттерны.

**Кодер может навредить машине?** Он выполняет код в WSL от имени пользователя. Защита: запрет деструктивных команд в промпте, подтверждения опасных команд Hermes (Approved once), данные только из TASK. Для продакшена — `terminal.backend: docker` (изоляция, read-only root, без capabilities).

### E.6. Деньги и производительность

**Сколько стоит один запрос?** Один вызов ≈ 15K входных токенов (у кодера мы видели `~15.6K`); запрос пользователя = 10–20 вызовов. На Haiku — центы за запрос. **[ЗАПОЛНИТЬ: фактический расход из console.anthropic.com → Usage]**

**Как снизили стоимость?** Haiku для всех; отключили background review; сократили набор инструментов; отключили reasoning в default-профиле; координатор сам отвечает на тривиальное.

**Сколько длится запрос?** Тест 2: ~1 минута (план → кодер пишет и запускает скрипт → график → финал). Полная цепочка с поиском — 1–3 минуты. **[ЗАПОЛНИТЬ по факту]**

### E.7. Каверзные вопросы

**«Это же просто три чат-бота с промптами?»** Нет: каждый — полноценный агент с циклом рассуждение→инструмент→наблюдение (кодер реально запускает Python, исследователь реально ищет в сети), собственной памятью и навыками; взаимодействие — по протоколу с ID, статусами, лимитами и многоуровневой защитой.

**«Почему все агенты на одной модели, если вы разделяете ради разных моделей?»** Бюджет. Архитектура поддерживает разные модели (одна строка в `config.yaml`); мы описали, какие поставили бы и почему, и наблюдали ограничения маленькой модели на практике.

**«Что будет, если координатор упомянет бота в финальном ответе?»** Этот бот проснётся. Специалист увидит, что это не TASK, и (в идеале) промолчит; маленькая модель напишет «нет задачи» (F8). Цикла не будет: у специалиста `bots_require_mention: true`, а координатор на сообщение специалиста без реплая на свой TASK… — и даже если ответит, сработают лимит делегаций и `bot_loop_guard`.

**«Почему у координатора выключены защиты, которые есть у специалистов?»** `bots_require_mention`/`exclusive_bot_mentions` = false у координатора — **осознанно**, чтобы доставка результата не зависела от того, правильно ли модель написала `@` (F7). Разрыв цикла обеспечивается на стороне специалистов (`true`), плюс `bot_loop_guard`.

**«Покажите, где хранится память агента»** → `ls ~/.hermes/profiles/coordinator/` и `cat ~/.hermes/profiles/coordinator/memories/MEMORY.md`; `hermes -p coordinator sessions list`.

**«Что вы делали сами, а что ИИ?»** **[ЗАПОЛНИТЬ честно.]** Важно понимать каждую строку конфигов и уметь объяснить решения — этот документ для этого.

### F.2. Демо (~4 минуты)

   ```

   ```
   Комментировать: «координатор пишет план → `@researcher [T1] TASK` → исследователь ищет (в окне gateway видно web_search) → RESULT с источниками → `@coder [T2] TASK` с данными → график → FINAL ANSWER без упоминаний = конец».

cd ~/hermes-telegram-team

# применить изменения из agents/ или .env
./scripts/setup.sh

```

/new@coordinator…_bot   /new@researcher…_bot   /new@coder…_bot   — новая сессия каждому

### G.3. Словарь

| Термин | Значение |
|---|---|
| **Агент** | LLM + цикл «подумать → вызвать инструмент → посмотреть результат → повторить» |
| **Hermes Agent** | Open-source фреймворк агентов от Nous Research |
| **Профиль** | Изолированная папка состояния Hermes (конфиг, промпт, память, история) |
| **Gateway** | Процесс-мост между агентами и мессенджерами |
| **Multiplex** | Один gateway обслуживает несколько профилей |
| **SOUL.md** | Системный промпт / личность агента |
| **Skill** | Процедурная инструкция, подгружаемая по необходимости |
| **Toolset** | Группа инструментов (web, terminal, file…), включается/выключается целиком |
| **Session** | Один непрерывный разговор; в Telegram длится до `/new` |
| **MEMORY.md / USER.md** | Долговременная память агента / профиль пользователя |
| **state.db** | SQLite-база всех сессий и сообщений |
| **Handoff** | Передача подзадачи другому агенту |

| **Bot-to-Bot mode** | Режим Telegram, разрешающий ботам получать сообщения других ботов |
